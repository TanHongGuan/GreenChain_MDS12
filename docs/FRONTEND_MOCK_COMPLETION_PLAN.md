## 2. Feature-by-feature gap assessment and implementation specification

### F1. Company and building management — existing core

**Reuse:** `ProjectsPage`, `ProjectDetailPage`, `UploadPlaceholder`, `AuthContext`, `RoleRoute`, `dataService`, `mockService`, existing project cards/status classes. **Missing:** company-scoped building list, create/edit building form, building metadata/detail management and explicit building selection on upload. A company workspace should be an operational table/list, not a second public discovery dashboard. Do not change catalogue comparison or automatically expose private draft details to Viewer.

**Candidate mock entities/fields:** `organisation {id,name}`; `membership {user_id,organisation_id,role}`; `building {project_id,organisation_id,name,location,building_type,reporting_boundary,floor_area_m2?,created_at,updated_at}`; provenance of owner and draft/active status if needed. These are **candidates**, not final shared API names. Keep existing `project_id`, `project_name`, `organisation` adapters for old fixtures.

**Actions/state:** Uploader opens My Buildings → creates building → sees it in own list → edits allowed metadata → selects it for upload. Validate required name/organisation, trim input, reject duplicate name within mock organisation, preserve stable ID and all prior submissions when editing. Edits must not rewrite an approved submission's historical values. Existing free-text upload can remain temporarily for regression, but new route should guide users to select an owned building; do not silently take ownership of seeded projects from another organisation.

**Access:** UPLOADER/company sees own mock buildings and create/edit commands; AUDITOR and VIEWER can use public discovery but cannot mutate company records. Mock role/ownership filters are UX simulation only. **Dependencies:** first establish mock organisation/membership identity and seed migration. **Likely files:** modify `src/App.jsx`, `src/components/Navbar.jsx`, `src/auth/permissions.js`, `src/mocks/{store.js,mockService.js}`, `src/services/dataService.js`, `src/pages/UploadPlaceholder.jsx`, `src/styles.css`; add `src/pages/CompanyBuildingsPage.jsx`, `src/pages/BuildingFormPage.jsx` or a focused form component, and tests.

**Acceptance/tests:** Creating/editing a building updates My Buildings, its detail and upload selector after route navigation/reload; same-name duplicate and missing required fields show errors; editing cannot change organisation or erase submissions; foreign mock building cannot be edited; Viewer/Auditor see no mutation route/link; current public catalogue/upload tests remain green. Cover service transitions and route gating, not only button visibility.

### F2. Certification scheme selection — proposed certification enhancement

**Reuse:** building form/detail and shared select/status UI. **Missing:** deliberate choice of scheme/category/version and safe change flow. The UI may offer *illustrative planning tracks* named GBI NREB and GreenRE ENRB only after a clear “Demo planning, official requirements not loaded” label. Keep scheme choice independent of submission review status. **Actions/state:** select/edit planning track, confirm before changing track when evidence links exist, retain old workspace as read-only snapshot or require explicit reset in mock state; never silently remap evidence. **Access:** owner Uploader edits; assigned Consultant may inspect; Viewer sees at most a plainly labelled preparation summary, never internal evidence. **Dependencies:** F1 and canonical mock preparation entity. **Likely files:** new `src/pages/SchemeSelectionPage.jsx`, mock seed/service, routes/nav/context actions, styles/tests.

**Acceptance/tests:** No scheme displays a neutral empty state; selection persists in session; changing scheme warns and preserves or explicitly clears links; unknown scheme/version cannot be asserted as official; current approved-data charts are unchanged.

### F3. Certification preparation workspace — proposed certification enhancement

**Reuse:** `ProjectDetailPage` metric summaries/history, `SubmissionRecords`-style trace labels, shared tables/status pills and loading/error patterns. **Missing:** preparation overview, illustrative checklist, evidence mapping, gap summary, per-item comments/NA rationale, and separate preparation progress. Use generic items such as “Electricity reporting evidence”, “Water reporting evidence”, “Emissions reporting evidence”, and “Supporting document placeholder”, all prominently **Illustrative demo checklist — not official GBI/GreenRE criteria**. Avoid invented criterion IDs, weights, pass thresholds and scores.

**Candidate fields:** `checklist_item {id,preparation_id,label,kind,illustrative:true,required_for_demo?}`; `evidence_link {id,item_id,submission_id?,artifact_ref?,note?,linked_by,linked_at,review_state}`; `item_state {status: MISSING|ATTACHED|INTERNAL_REVIEWED|NOT_APPLICABLE,na_reason?,comment?}`; `preparation_event {actor_id,action,at,subject_id}`. A link to a mock submission must retain the exact `submission_id`/period/status; if it changes, show a stale warning rather than silently replacing it. Simulated documents may be metadata-only, with no false real file storage/receipt claim.

**Actions/state:** owner links/unlinks existing submission evidence or adds document metadata, adds notes and justified N/A, views missing items; assigned consultant comments/marks internally reviewed; only approved submissions may count toward a clearly named *demo preparation completeness* numerator if the team chooses that policy. Document formula in UI/tests, exclude NA consistently, and display “no official readiness or score computed.” **Access:** Uploader edits links/notes, assigned Consultant reviews, Viewer gets no private evidence workspace. **Dependencies:** F1, F2, F4 assignment design, and seed migration. **Likely files:** new `src/pages/PreparationPage.jsx`, `src/components/PreparationChecklist.jsx`, `src/utils/preparation.js`, mock service/store methods, routes/styles/tests.

**Acceptance/tests:** Missing evidence remains visibly missing; linking/unlinking changes item state and count in every view; unreviewed/rejected data are not silently treated as approved; NA needs reason; stale/missing submission link is surfaced; consultant comment does not turn internal review into official certification; no backend request occurs in mock mode.

### F5. Consultant review enhancements — existing core extension + proposed assignment scope

**Reuse:** `ReviewPlaceholder`, `getPendingReviews`, `getReviewDetail`, `decideSubmission`, simulated evidence, existing confirmation/integrity warning/history. **Missing:** assignment-filtered queue, exact-version evidence context, richer validation findings (illustrative), required negative reason, criterion-level comments and optional request-changes workflow. **State policy:** keep current `UNREVIEWED → APPROVED|REJECTED` intact; design `CHANGES_REQUESTED` as an additional **mock-only** state after team agrees whether it replaces rejection or coexists. Do not alter real API adapter or assume it accepts new decision values. A corrected resubmission should create a **new** submission ID with `previous_submission_id`, leaving the earlier version/history intact.

**Candidate fields:** `review {id,submission_id,reviewer_id,decision,reason,reviewed_at}`; `validation_finding {id,submission_id,severity,row?,message,illustrative:true}`; version links and preparation comment references. **Actions/state:** consultant filters own queue, opens original/processed *simulated* evidence, checks integrity label, approves/rejects with confirmation; negative decision requires reason; if enabled, requests changes, owner resubmits and links version. Scope and evidence privacy must be applied at mock service methods as well as route UI. **Access:** only accepted assigned Consultant can decide; owner sees decisions on own submissions, Viewer sees approved-public values only. **Dependencies:** F4 and F3 criterion comments; request-changes can be deferred until state policy agreed. **Likely files:** modify `ReviewPlaceholder.jsx`, `UploadPlaceholder.jsx`, mock service/store, `ProjectDetailPage.jsx`, tests; perhaps extract review detail component only if duplication warrants it.

**Acceptance/tests:** Existing approve/reject still update approved analytics correctly; second/conflicting decision returns 409-style mock error; reviewer attribution and reason persist; changed submission becomes a new version; unassigned mock user cannot inspect or decide; pending/decision/empty/error states work; no simulated evidence is presented as a genuine stored file.

### F6. Application preparation and simulated export — proposed certification enhancement

Export may be allowed with gaps only if clearly marked incomplete. **Access:** owner and assigned Consultant only; Viewer cannot access private package. **Dependencies:** F3/F4/F5, agreed mock package content. **Likely files:** new `src/pages/PreparationExportPage.jsx`, `src/utils/mockPackage.js`, service/store events, route/styling/tests.

**Acceptance/tests:** Manifest references stable submission/evidence IDs and exact versions; missing/duplicate references are flagged; generated file opens and matches preview; role checks prevent UI/mock-service access for Viewer/unassigned consultant; package is labelled “Demo preparation package — not official certification or submission”; export event does not mutate approved metrics.

### F7. End-to-end mock state consistency — existing-core infrastructure
